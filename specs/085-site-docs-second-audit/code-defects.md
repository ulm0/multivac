# Behaviour documented as it is, that reads as a code defect

The pages in this change say what the 0.15.0 code does. The writers and checkers met the behaviours below while doing so, and left the code alone (FR-003): each is a candidate for the roadmap, not a decision. Each line is a lead from a writer reading `src/`; verify it before acting on it.

1. `multivac doors` in a brain that is not a git repo writes AGENTS.md, then dies with a raw `Command failed: git -C <dir> config core.hooksPath .multivac/hooks` / `fatal: not in a git directory` and exits 1. installHooks (src/hooks/install.ts:449) runs execFileP('git', ... 'config', 'core.hooksPath', ...) with no catch. The page now describes only what doctor shows.
2. `multivac doctor` has no gitless-brain message. A non-git brain gets only `core.hooksPath unset → git config core.hooksPath .multivac/hooks`, because the git config read failing is treated as unset (doctor.ts hooksLine). Following that advice fails.
3. `seed` reports any declared repo path whose `git ls-files` fails, including an existing plain directory that is not a git repo, as `not present; run multivac repos sync to clone` (seed.ts, catch around lsFiles). The message misdescribes a present non-git directory. The page now says only that seed lists a repo it cannot read under `skipped`.
4. On a retired row, an `absent` leg that predates the retirement keeps gating, because the lifecycle filter cannot tell it from an authored tombstone (verify.ts evalAnchors). Documented as is on invariants.md; a code decision may be wanted.
5. In a `verify --strict --range` CI run, the index-reading checks (enactment, config-modified, law removal) print 'not answered' by construction, so a commit that skipped the hook and broke one of them passes the pipeline. Documented as is on brain-driven-development.md.
6. src/commands/doors.ts: `doors` in a git-less brain writes AGENTS.md and then dies with a raw `Command failed: git -C <dir> config core.hooksPath ...` (exit 1) instead of a clear message. Not touched in this repair; the page only says doctor shows the hooks unarmed, which doctor.ts:627 does (`core.hooksPath unset -> git config core.hooksPath .multivac/hooks`).
7. Possible code wart, documented as-is: the strict gate for a finished change attributes a doubly-declared claim to the first change file in filename order (verify.ts finishedChanges comment), so a genuinely finished second change can be invisible to `verify --strict`.
8. change.ts baseNames/branchBase: apply's default-branch resolution has a last resort of HEAD (the checked-out branch, whatever it is) when none of origin/HEAD, init.defaultBranch, main or master exist, so a busy repo can branch from somebody else's change branch; the page's 'never a fixed name' wording does not mention this fallback.
