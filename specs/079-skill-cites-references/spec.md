# Feature Specification: The skill carries what no command prints, and no page keeps a sentence the tool contradicts

**Feature Branch**: `079-skill-cites-references` | **Created**: 2026-09-29 | **Status**: Draft
**Input**: User description: "The multivac skill is cut to a core that states the rhythm, where you are, seven rules and where to read what, and each reference keeps only the judgement no command prints, naming the surface that prints the rest: the brain door, the lifecycle's lines and refusals, `verify`'s lines, `mvac help anchor`, the seed report. The pointers hold in every configuration, a code repo behind a consumer door included. Every sentence the tool contradicts is retired from the skill, the root documents, the constitution and the site, each family pinned by an `absent` leg on the row that retires it; this change is the backstop for the families changes #5–#8 own. The pre-plan leftovers go, and DESIGN and the composition page each say once that the tool is adapter first with an always-available fallback. Adds MV-152; lands after graph-answers-where-asked, codegraph-worktrees-and-verbs, change-file-cites and verify-rooted-and-quiet, and re-derives every figure and the trimmed pack on the tree where they merged."

### User Story 1 - A change session loads only what no command prints (Priority: P1)

An agent in Claude Code opens a change in a brain. The multivac skill triggers on
"planning, applying, landing, closing" and its table sends the agent to the change
reference, so the session loads the skill body and `references/change.md`: 25,855
bytes at 62d4588 (28,219 on graph-answers-where-asked's branch, a projection). About
60% of the 50,455-byte pack says again what the brain door (loaded every session), the
lifecycle's lines and refusals, `verify`'s lines, `mvac help anchor` or the seed report
print at the moment they apply — two door clauses verbatim. Nine of its sentences were
false or stale.

**Why this priority**: it is the saving, paid in nearly every change session, and it
removes the pack's false sentences at the same stroke.

**Independent Test**: on the new pack, run the pack tests and the restatement test on
this brain's own configuration, then measure the skill bytes a change session loads.

**Acceptance Scenarios**:

1. **Given** the merged pack, **When** every paragraph is classified said elsewhere, only here or false against the merged tree's surfaces, **Then** the new pack keeps every only-here paragraph, turns each said-elsewhere paragraph into a pointer naming its surface or drops it, and corrects or drops each false one.
2. **Given** the new pack, **When** a change session loads the body and the change reference, **Then** it loads at most 10,000 bytes, and at most 40% of the same session measured on the merged tree before this change.
3. **Given** the new body, **When** the agent reads it, **Then** it states the rhythm `change new → plan → apply → land → close`, says each step says what it did and what it left to you and each refusal names what it looked for and the command that fixes it — "run what they print" — and then where you are, seven rules and where to read what.
4. **Given** the new pack, **When** this brain's own door (brain==code, spec-kit, graphify) is rendered, **Then** no clause of 30 characters or more of it appears in the pack.
5. **Given** any law leg that reads skill text, **When** it is counted on the new pack, **Then** it counts what it counted on the merged tree before this change.
6. **Given** the two committed copies of the pack, **When** `multivac doors` runs, **Then** they are byte-identical.

### User Story 2 - The pointers hold in every configuration, a code repo included (Priority: P1)

A pointer is only a saving if the surface it names prints the thing. The skill is
projected by the `claude` target into the brain and into every managed code repo, so
it also loads behind a consumer door. There the consumer door lists no SDD step and no
`multivac change`, and `change new` advised `multivac init .`, which turns a code repo
into a second brain. `change plan` prints no next step without an SDD. A grapher
declared under `graphers:` has no verbs; with no grapher the door says nothing about
one; `change apply` prints a graph flag only where a grapher is declared. The `read`
lines state a fact and no fix.

**Why this priority**: without it the trimmed pack sends an agent to a line that is not
printed, which is worse than the bytes it saves.

**Independent Test**: render the brain and consumer doors of every configuration of the
matrix and run the restatement test over them; walk the lifecycle in five scratch
ecosystems and tick each pointer against a printed line.

**Acceptance Scenarios**:

1. **Given** a session in a code repo behind a consumer door, **When** the agent follows the skill, **Then** it writes code in the worktree `change apply` printed, runs `verify` there, runs `change`, `roadmap` and `seed` in the brain's own checkout (never in the mount), reads the brain's door there, and never runs `multivac init` in the code repo, whatever a refusal there says.
2. **Given** a brain whose door names a grapher with verbs, one declared under `graphers:` with none, or no grapher, **When** the agent follows the grapher pointer, **Then** it uses the named verbs, greps where the door says there are none, and greps where the door names no grapher.
3. **Given** a change in a configuration with no grapher, **When** the agent reads the skill, **Then** nothing promises that `change apply` prints a graph flag.
4. **Given** `sdd_auto: false` or no SDD, **When** `change plan` prints no next step, **Then** the rhythm the core states still names `apply` as next.
5. **Given** a `read` line that fell back to the working tree, shows an old fetch, or shows the brain behind its own channel, **When** the agent reads the verify reference, **Then** it finds what to do before believing a red.
6. **Given** the restatement test, **When** it renders every configuration of its matrix, **Then** each fixture's door carries the marker of its own shape and the pack restates none of its clauses.
7. **Given** a fresh ecosystem built with the new build, **When** `repos sync` and `doors` run, **Then** the brain and each managed code repo hold a byte-identical skill copy and a read-only repo holds none.

### User Story 3 - No sentence the tool contradicts survives in the skill, the docs or the constitution (Priority: P1)

A retired sentence retires every copy (MV-111). At 62d4588 the claim that `close`
checks "law and code ended consistent" had 16 copies in nine files, one of them
Principle III of the constitution that `/speckit.plan`'s Constitution Check reads; the
graph's refuted saving, four; the skill's own false phrases, nine; "`close` commits
it", four. The owning changes #5–#8 were handed the copies their rows retire; this
change is the backstop for every family and owns the rest.

**Why this priority**: each copy is a sentence an agent or a reader acts on, and
several sit in agent-read files.

**Independent Test**: on the merged tree, count each family's alternatives over its glob
and over the rendered doors and flow.md of the configuration matrix; after the edits,
count again.

**Acceptance Scenarios**:

1. **Given** the merged tree, **When** each family is counted alternative by alternative, **Then** a family its owner pinned and left at 0 gets nothing here, a family with hits is fixed here and pinned on MV-152 with the owner's miss recorded, and a family at 0 that no row pins gets its leg on MV-152.
2. **Given** the constitution, **When** the Constitution Check reads it, **Then** Principle III says `change close` verifies the rows the change claims, and the Compliance section qualifies "on every commit" to where the hooks are armed.
3. **Given** the site, DESIGN.md and the skill, **When** they describe what a graph returns, **Then** none says it answers in fewer calls or bytes than a search.
4. **Given** the pages that describe a code-less brain's specs at close, **When** they say what `close` does, **Then** they say `close` names them in the archive commit it prints, never that it commits them.
5. **Given** a family's leg, **When** it is added, **Then** it lands in the same commit as the edit that turns it green.

**Acceptance Scenarios**:

2. **Given** the Cursor section and samples, **When** a reader looks for what Cursor gets, **Then** it reads `AGENTS.md` natively and no rules file is named as written.
3. **Given** composition.md, **When** it says when the graph is refreshed and what `change land` commits, **Then** it says the post-edit hook only where the harness has one, otherwise at land and close, and that a local index is never committed.
4. **Given** DESIGN.md and the distribution page, **When** they describe the skill, **Then** they say it carries what no command prints and names the command that prints the rest, that multivac installs it only for Claude Code, and that `doors` mirrors the skill directory — and nothing there contradicts the session-zero text.

### User Story 5 - One place says adapter first, fallback always; the small corrections ride along (Priority: P3)

No page tells the plan's story once: a declared tool carries its own work; multivac adds
the gate, the pointer and the files it says it writes; with none declared, the work
runs as before. Four copies say "no install step to forget" though a fresh clone has no
hooks armed until `doors` runs; DESIGN says multivac "never installs anything" though
it runs vendor installs; the close samples and the `sdd_auto` sentence name the wrong
paths and points.

**Why this priority**: correctness and orientation for readers, with no session saving.

**Independent Test**: count U1, U2 and A7; replay each close sample in the fixture it
asserts.

**Acceptance Scenarios**:

1. **Given** DESIGN.md, **When** a reader looks for the principle, **Then** one subsection states it, lists per row the configurations it covers, and copies no row's numbers.
2. **Given** the composition page, **When** a user reads it, **Then** one section states it in plain words with no law ID and no version string.
3. **Given** the close samples, **When** each is replayed in the fixture its text asserts, **Then** the printed pathspecs match.
4. **Given** the CHANGELOG, **When** the release is cut, **Then** its Unreleased section names MV-152 with the figures measured at the end of this change.

### Edge Cases

- A session in a code repo (the skill loads behind the consumer door): the core's *Where you are* paragraph sends lifecycle commands to the brain's checkout; a code repo's `change new` refusal still says `multivac init .` until verify-rooted-and-quiet or a follow-up names the enclosing brain (a ceiling here).
- A `managed: false` or shallow repo: no skill copy is projected there; nothing in the pack assumes one.
- A brain with no `claude` door target: multivac writes no skill copy, yet `init` and the empty-brain door still say to load it (MV-70's shape). Out of scope here, a named follow-up; the new DESIGN and distribution sentences do not contradict the session-zero text.
- A bare close by an agent that used to get by on the body alone: it now reads body plus change reference, about +2,100 bytes at 62d4588 — the worst case, stated.
- A code-less brain with per-repo graphers only, or mixed graphers: if its door does not name each grapher's verbs on the merged tree, a two-row verbs table stays in the core.
- An owner's feature did not land as designed (the quiet line, the close citation gate, apply's graph flag, codegraph's symbol form): the pack sentence that relies on it carries the pre-feature truth instead.
- A family's owner fixed every copy but pinned only some alternatives: the unpinned alternatives get MV-152's leg.
- A paraphrase of a door clause, a restated lifecycle or `verify` line, or a configuration the test does not render: passes the restatement test (a ceiling).
- A retired phrase reflowed across two lines, or a new paraphrase: passes the line-local `absent` legs (a ceiling).
- The `.claude/skills/multivac/` copy is tracked, not a symlink: the skill legs read `skills/multivac/`, the retired-sentence legs read both copies, and the copy test keeps them identical.
- `CHANGELOG.md`, `.multivac/invariants.md` and `specs/` are outside every family's glob: history and the law may quote a retired phrase.
- A true sentence that shares words with a family: each regex is probed on the correct listing it must not match (the three-shim listing, the retired Cursor path named as retired).

## Requirements *(mandatory)*

### Functional Requirements

#### The core (US1)

- **FR-001**: The skill's frontmatter MUST stay byte-identical — its name and its description with the five triggers the pack test pins, listed in every Claude Code session — and its H1 MUST stay `# multivac — operating protocol` (MV-72).
- **FR-002**: The skill body MUST carry exactly: the contract (the brain door says where the law is, which repos exist, which grapher and SDD bind and what each SDD step proves; the rhythm `change new → plan → apply → land → close`, which `multivac change` lists; each step says what it did and what it left to you, each refusal names what it looked for and the command that fixes it: "run what they print"); *Where you are* (FR-013); session zero's one question and its `repos:` sentence (MV-136); seven rules (FR-003); a table of where to read what, naming each reference and `mvac help anchor`; and the grapher and ecosystem-graph pointers (FR-015).
- **FR-003**: The seven rules MUST be: (1) verify is never skipped, never `--no-verify`; (2) read the `read` lines before the verdicts (MV-53's sentence kept), with the quiet fold where the quiet line shipped; (3) cite claims by ID "everywhere law is referenced", the one deliberate restatement of a door clause, which MV-126 reads; (4) never relax an invariant in code: the row changes first, dated, in the same change, and `close` verifies only the rows the change claims, so claim the row you amend; (5) you propose, the human enacts, and `close` enacts nothing; (6) code lands on a change's branch (MV-141's sentence kept), written only in the worktree `change apply` prints, with MV-137's conditions: where an SDD governs and `sdd_auto` is on the brain's own checkout refuses code elsewhere at commit, a code repo's hook reports it and CI's `verify --strict --range` refuses it; (7) the roadmap is never a gate, and `change new` on a planned slug promotes it (MV-89's sentence kept).
- **FR-004**: The change reference MUST keep only what no command prints: `multivac change` lists the steps, `new`, `apply` and `land` commit their own bookkeeping and `close` prints the archive commit; the run-the-chain sentence; `planned` (MV-89's heading), promotion never a precondition, the one-way projection; never pick an ID; the four fields, stages with no edge form (MV-111's arrow leg stays 0), claims as IDs; the worktree, the carry "**carried onto the branch**" (MV-141), a code-less brain's SDD files named in the commit `close` prints; `land` commits a shared code graph on the branch, never a local index; the merge request is yours and `--landed` records your statement; `close` refuses until every claim resolves and cites a row the change adds or touches that states its rule, a merely touched row verified there only when claimed, every other row reported by `verify` on each commit where the hooks are armed and refused only in a blocking mode or under `--strict`; close enacts nothing; the graph gate is existence, not freshness; the ritual, and an empty ritual is not permission; mid-change decisions become claims; the graph section (MV-52's heading) as a pointer; the SDD flow section (MV-51's heading) stating the task-ledger close gate, the ungateable steps run anyway, the brain's project document and MV-57's phrase, opsx's `context:` reported never gated; retiring, with two example anchors and step 5 "from then on the new `absent` legs gate every run: a retired row's tombstone blocks by default". It MUST NOT say a step prints the next one unconditionally, that `close` commits anything, or advise claiming a retired row.

- **FR-009**: The five reference file names MUST stay as they are: the seed report and `init` print two of them, and `init` says the skill "carries both protocols".
- **FR-010**: The new pack MUST be derived on the tree where graph-answers-where-asked, codegraph-worktrees-and-verbs, change-file-cites and verify-rooted-and-quiet have merged, by classifying every paragraph of that tree's pack as said elsewhere (naming the surface that prints it there), only here, or false, never by copying the design's prototype; every fact those four changes put into the skill that no command prints on the merged tree MUST be kept — the quiet qualifier (and the "Quiet" paragraph unless `verify --quiet` prints the same), claims as IDs and close's citation gate, codegraph's symbol form unless the rendered codegraph door names it — and what their doors and `apply` print MUST become pointers.

### Key Entities

- **Skill pack**: the core (`SKILL.md`: frontmatter, body) and five references, shipped in `skills/multivac/` and projected byte-identical by the `claude` target.
- **Paragraph classification**: per paragraph of the merged pack, one of said elsewhere (with the surface named), only here, or false; the rule that turns it into the new pack.
- **Pointer**: a sentence of the pack that names a surface — the brain door, a lifecycle line or refusal, a `verify` line, `mvac help anchor`, the seed report — and the condition under which that surface prints it.
- **Retired-sentence family**: a set of phrases the code contradicts, with its copies, its glob, its owner row and the decision taken on the merged tree.
- **Door fixture**: a configuration the restatement test renders, with the marker its door must carry.
