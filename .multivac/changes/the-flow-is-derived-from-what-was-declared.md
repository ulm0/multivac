# One page saying what is automatic, what is a gate, and what is yours

A newly initialised brain has no single place saying what multivac enforces for
you versus what is yours. The law is ninety rows; the ritual is empty. The
reasonable conclusion from reading a fresh repo is that nothing is enforced,
which is false and is the tool's fault.

A document derived from the config and the adapter registry, regenerated by
`doors` with a managed block the way the door already is, sorting every
obligation into three columns: **automatic** (multivac does it, unasked),
**gate** (multivac refuses without it), **yours** (nobody can check it; it lives
in the ritual). With `sdd: speckit` those rows write themselves — the registry
already carries the exact `ungateable:` reasons, to be reused verbatim rather
than re-worded.

The load-bearing distinction: derived files are rewritten freely, authored files
are never overwritten. The ritual is authored; this is derived.

**The first design was killed in review, and the reason is the hard part.** It
cited `MV-nn` ids in the generated page. Invariant ids are LOCAL TO EACH BRAIN —
allocated from that brain's own table, and `init` writes a table with zero rows
— so every citation would dangle or collide in any brain but this one. A second
warning from the same review: written loosely, this page becomes an unanchored
second law table that reads authoritative and drifts, which is the tool
committing MV-46 against itself. Containment: a row goes in only if it is
adapter data rendered through an existing helper, or a pointer that names no id
at all.
