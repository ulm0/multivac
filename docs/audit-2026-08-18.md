## `CIT-1` — `--flag=value` was accepted in 0.8.0 and is refused in 0.9.0

**Severity**: high. A published release rejects a form the previous one wrote to
disk, and the change that caused it promised it would not.

**Reproduce**, both builds, same argument:

```txt
$ mvac init --provider=claude --quiet "$T"     # 0.8.0
exit 0        · config.yml contains claude

$ mvac init --provider=claude --quiet "$T"     # 0.9.0
init: unknown flag --provider=claude — known: --provider <a,b>, --sdd <name>, --grapher <name>, --quiet
exit 2
```

Same for `--sdd=speckit` and `--grapher=graphify`.

**Why it happens.** `init`'s old `parseFlags` split on `=` explicitly —
`const eq = a.indexOf('=')` — so the equals form was parsed. MV-104 moved
parsing to citty, which also understands `=`, but put `undeclared` in front of
it, and `undeclared` compares WHOLE tokens against the declared names: it never
splits, so `--provider=claude` matches neither `--provider` nor any flag, and
the parser that would have understood it is never reached.

**What makes it a defect rather than a decision**: the change's own spec says
the opposite. FR-003 — *"Parsed values MUST be identical to today's for every
declared argument form, including `--flag value` and `--flag=value`"* — and
SC-003 — *"No command's output, exit code or refusal wording changes"*. The
suite did not catch it because `test/cli/args.test.ts` asserts that citty parses
`--repo=api` and separately that `undeclared` accepts `--repo api`. It never
asks the pair about the same input, which is precisely the seam the change
introduced.

**Impact.** Anyone whose script or docs used the equals form gets exit 2 from a
minor release. The other valued flags — `verify --repo`, `roadmap --horizon`,
`change --landed` — refused the equals form in 0.8.0 too, so for those this is
an inconsistency rather than a regression: the parser under them understands a
form the refusal in front of them rejects.

**Proposal.** Split on the first `=` in `undeclared` before matching, so a
`--name=value` token is tested as `--name`. Roughly three lines in
`src/lib/args.ts`, plus the test that was missing: one input, both readers.

## `REG-1` — `[:digit:]` outside a bracket expression still compiles to a regex that matches nothing real

**Severity**: high. Unchanged since the last pass. Silent false green in a
blocking mode.

```txt
$ node -e "import('./dist/lib/regex.js').then(m=>{const r=m.compileAnchorRegex('PIN[:digit:]'); console.log(r.source, r.test('PIN4'))})"
PIN0-9 false
```

`PIN[[:digit:]]` compiles to `PIN[0-9]` and matches `PIN4`. The one-bracket
version — the canonical mistake — compiles clean and matches only the literal
text `PIN0-9`, so a tombstone written that way is green forever while real
violations sit in the glob. GNU grep errors on exactly this input; multivac's
dialect gate, whose whole purpose is catching dialect mistakes at write time
(MV-05), accepts it.

**Proposal.** Track bracket state in the walk `compileAnchorRegex` already
performs and throw `RegexDialectError` for `[:name:]` outside `[...]`.

## `CNT-1` — `count` still reads the working tree while `verify` reads the channel

**Severity**: medium. Unchanged since the last pass.

`src/commands/count.ts:114` builds `new RepoScanner(t.dir)` with no ref, and no
ref means the working tree. `verify` reads a sibling repo at its channel ref
(MV-53) and prints a `read` line naming what it read; `count` prints no such
line, so a pinned `count=N` can disagree with the number `verify` will compute
and nothing on screen explains the gap.

## `ONB-1` — a brand-new brain cannot open its first change, and the refusal misnames the state

**Severity**: low, and it is the first thing a new user meets. Present in 0.8.0
too, so it is not new — it is unnoticed.

```txt
$ mvac init --quiet .
$ mvac change new "points expire"
cannot open points-expire — bookkeeping paths carry uncommitted edits: .multivac/invariants.md
  commit them first: git -C … add -- .multivac/invariants.md && git commit
```

Two things at once. `init` scaffolds everything **untracked**, and `change new`
requires its bookkeeping paths to be clean — so the very next lifecycle command
after `init` always refuses in a fresh brain, while `init`'s closing
call-to-action names loading the skill, seeding and enacting, and never says to
commit what it just wrote. And the refusal calls an untracked file *"carries
uncommitted edits"*, which is the wrong word for a file that was never edited;
the command it prints is correct, which is what keeps this low.

**Proposal.** Either `init` commits its own scaffolding, or its closing lines
name the commit as step 0. The wording is a one-line fix whichever way that
goes: *untracked or modified* rather than *uncommitted edits*.

## Method, and its ceiling

Every finding was reproduced against a build of this commit before it was
written down, and `CIT-1` was diffed against a build of the previous tag rather
than recalled. Two harness slips were caught while measuring and are worth
naming, because they would have produced false findings: `printf` before a
command captures `printf`'s exit code, not the command's, and an unminified
build wraps `<meta>` attributes across lines so a single-line grep reports a tag
as absent. Both were re-run before anything was recorded.

Five areas were examined closely. Absence from this list is not evidence of
correctness.
