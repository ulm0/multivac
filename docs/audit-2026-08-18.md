## `REG-1` — `[:digit:]` outside a bracket expression compiles to a regex that matches nothing real

**Severity**: high. Silent false green in a blocking mode.

**Problem.** `compileAnchorRegex` translates POSIX classes with a context-free
rewrite: `[:digit:]` becomes `0-9` wherever it appears, not only inside `[...]`.
An author who writes the canonical forgot-the-outer-bracket mistake gets a
regex that compiles clean and matches only a literal string.

**Reproduce.**

```txt
$ node -e "import('./dist/lib/regex.js').then(m=>{
    const r = m.compileAnchorRegex('PIN[:digit:]');
    console.log(r.source, r.test('PIN4'), r.test('PIN0-9'));
  })"
PIN0-9 false true
```

`PIN[[:digit:]]` compiles to `PIN[0-9]` and matches `PIN4`, as it should. The
one-bracket version matches only the literal text `PIN0-9`.

The escape scan does not protect it either: `a\[:digit:]b` — a deliberately
escaped literal bracket — is rewritten to `a\0-9b`, and `\0` is a NUL escape in
a JavaScript regex, not the character the author wrote.

**Impact.** An anchor `<!-- @anchor X brain:src/** /PIN[:digit:]/ absent -->`
parses clean and evaluates green forever while real `PIN4` violations sit in the
glob. That is the silent false green the tool exists to prevent, in a blocking
tombstone mode, with no diagnostic anywhere. GNU grep ships a dedicated error
for exactly this input — *character class syntax is [[:space:]], not [:space:]* —
and multivac's dialect gate, whose whole purpose is catching dialect mistakes at
write time (MV-05), accepts it.

**Proposal.** Track bracket-expression state in the walk `compileAnchorRegex`
already performs, and throw `RegexDialectError` for any `[:name:]` found outside
`[...]`, with grep's own hint. Roughly ten lines in `src/lib/regex.ts` plus one
case in `test/helpers/regex.test.ts`.

## `DOC-1` — `doctor` documents a law gate it does not have

**Severity**: medium. A documented contract that fails open.

**Problem.** Three places state that `doctor` exits 1 on an invalid law:

- `src/commands/doctor.ts:719` — *exit 0 even when degraded; exit 1 only when the config/law is invalid.*
- `site/content/docs/reference/commands.md:671` — *its only exit 1 is a config or law that does not load*
- `site/content/docs/reference/commands.md:689` — *Invalid config/law stays exit 1 under both.*

The law is never judged. The one place `doctor` parses anchors discards the
diagnostics.

**Reproduce.**

```txt
$ mvac init --quiet .
$ printf '<!-- @anchor MV-99 brain:*.ts /[unclosed/ -->\n' >> .multivac/invariants.md
$ mvac verify        ; echo $?
0 blocking broken · exit 1 · 1 anchor parse errors
1
$ mvac doctor        ; echo $?
0
$ mvac doctor --strict ; echo $?
0
```

`doctor` prints nothing about the malformed row in either mode.

**Impact.** A machine-setup script that trusts the documented contract concludes
the brain is loadable while `verify` refuses every commit. The project's own
test says the truth out loud — `test/doctor/doctor.test.ts` titles its case
*invalid config is the one exit-1 case* — so the code and the prose have
disagreed since the sentence was written.

**Proposal.** Smallest fix that makes the words true: drop "law" from the three
sentences. Better for the same size: `doctorReport` already collects the brain's
anchors — keep the diagnostics it currently throws away, print them under a
`law` label, and exit 1 when any exist. Then the documented contract and the
`doctor`/`verify` agreement both hold.

## `CNT-1` — `count` reads the working tree while `verify` reads the channel, and says nothing

**Severity**: medium. Two commands, two answers, no line explaining the gap.

**Problem.** `count` builds its scanner with no ref:

```txt
src/commands/count.ts:102   const scan = await scanLeg(a, new RepoScanner(t.dir), [t.key]);
src/anchor/match.ts:36      this.list ??= this.ref ? lsTree(this.dir, this.ref) : lsFiles(this.dir);
```

No ref means the working tree, always. `verify` reads a sibling repo at its
channel ref and the brain at its working tree (MV-53), and prints a `read` line
per repo naming what it read. `count` prints no such line.

**Impact.** A sibling repo parked on a WIP branch with one extra match: `mvac
count 'api:src/*.ts /SECRET_KEY/'` prints 1, the author pins `count=1`, and the
next `verify` reads `origin/main`, finds 0, and blocks with *count=1 pinned,
found 0*. The wrong-ratchet outcome `count` exists to prevent. The command's own
help — *verify's own matcher* — is true about the matcher and silent about the
source, which is the half that differs.

**Proposal.** Either give `count` the same source resolution `verify` uses, or
print the `read` line it is missing so the difference is on screen where the
number is. The second is smaller and honest; the first removes the difference
instead of documenting it.
